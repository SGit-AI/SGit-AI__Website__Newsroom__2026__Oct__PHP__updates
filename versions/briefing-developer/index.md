The php2shell story for a developer: what to decide, the claims it rests on with their status and sources, and what is still open. Briefing · Developer # Is my code the problem, what do I change, and how do I check the box I deployed to? Your code is not the problem and cannot be the fix. The flaw is in the C engine that runs it. What you can do is check the box you deploy to and avoid making the engine's job harder. ## What to decide or do - Check the running version where the code runs: php -v inside the container or phpinfo() on the box, after the restart. The package list is not the answer. - Fixed: 8.5.12, 8.4.27, 8.3.36, 8.2.35. If your target is 8.1 or older there is no release; tell whoever owns the platform today. - Nothing in userland blocks the demonstrated paths: ini_set() runs too late, .user.ini runs too late, auto_prepend_file runs too late. The settings have to be in php.ini, the pool or the server config. - Fix attacker-reachable fatal errors and timeouts in your own code anyway: the advisory lists them as one of the paths for the stale-state bug. - After the patch, out-of-memory behaves differently: a delayed fatal at the next safe point instead of an abort, and a hard limit that ends the process.
